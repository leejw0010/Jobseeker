## 3. 확인한 결함과 수정

- **전형 삭제 후 상태 불일치:** 추가·편집·삭제를 같은 상태 계산 서비스로 연결했다. 신규 기록은 생성 시 기준 상태를 보존하고 결과 날짜 순으로 계산한다. 수동 변경은 명시적으로 해제할 때까지 유지한다. 과거 기록의 출처를 추측해 자동 전환하지 않는다.
- **legacy→manual 전환 후 기준 상태 누락:** 과거 기준이 없는 기록은 수동 변경 후에도 `state_requires_baseline`을 유지한다. 이벤트 기준 전환 시 사용자가 기준 단계·상태를 선택해야 한다.
- **전체 상세 응답이 최신 문항 저장/제출 결과를 덮음:** 문항 버전과 제출 확인 순번을 독립적으로 병합한다. 늦은 기본정보 저장·전형 추가·재조회 응답이 새 버전이나 제출 포인터를 과거로 되돌리지 않도록 회귀 사례를 추가했다.
- **확인되지 않은 초안을 실제 제출처럼 취급할 위험:** 기존 `is_submitted`와 sync 기본값은 호환성을 위해 보존하고, 명시적 제출 확인 이력을 분리했다. UI는 `confirmed`, `legacy_unverified`, `none`을 구분한다.
- **직접 DB 접근으로 과거 답변 변경/제출 이력 손상 가능:** PostgreSQL과 SQLite의 이력 가드가 과거 본문·소속·버전 번호 변경, 제출 표시 취소, 단독 버전 삭제를 막는다. 사용자가 명시적으로 부모 문항/지원 건을 삭제하는 경로는 DB cascade로 정리한다.
- **지원월 오인·통계 중복:** 실제 지원일만 새 월별 화면에 집계한다. 과거 합격과 현재 탈락을 한 단계에서 동시에 세지 않도록 유효 현재 상태에 따라 계산한다.
- **확장의 자동 수집·인증 상태 잔존:** 공고 메타데이터 읽기는 사용자 버튼으로 시작한다. 401은 실패 요청의 토큰만 정리하고, 로그아웃·사용자 변경 시 이전 화면/진행 응답을 무효화한다. 작성 중 자소서 자동 수집은 추가하지 않았다.
- **Practice의 숨은 직접 입력이 Track 기준을 덮음:** 지원 건 선택 시 생성 요청에서 직접 입력 회사/직무/자소서 필드를 제외한다.
- **저장 후 재조회 실패로 오래된 코칭이 다시 보임:** PATCH 성공 즉시 관련 로컬 코칭·디브리프·재연습 캐시를 무효화한다. 최신 GET 성공 전까지 종합 해석을 멈추고 실패 시 재조회 버튼을 제공한다.
- **전사문 초안 중 종합 스크립트가 남음:** 앞선 답변 초안의 영향을 받는 이후 코칭과 전체 종합 스크립트·행동 제안을 보류한다. 회고 메모만 바꾼 경우 답변 자체 코칭은 유지한다.
- **Gaze 종료 버튼 접근 불가:** 측정 overlay 위에서 중단 버튼을 누를 수 있게 하고 invalid/aborted 결과를 사유와 함께 내보낸다. 정확도 임계값은 바꾸지 않았다.

- **연결된 지원 건과 질문 목록 불일치:** 다른 지원 건에서 만든 질문을 선택 목록에 노출해 시작 시422가 발생했다. 연결된 지원 건과 무연결 질문만 표시하고 지원 건 변경 시 선택을 초기화했다. 생성 중 삭제가 대기 상태를 먼저 풀던 중첩 경합도 동기 실행 가드와 버튼 비활성화로 재현·수정했다. 기존 서버 차단은 그대로다.

독립 부분 리뷰의 Important 항목은 위 legacy 기준·상세 응답 경합·직접 DB 불변성과 Practice의 숨은 입력·저장 후 재조회·초안 종합 스크립트였다. 수정 후 부분 재리뷰는 모두 addressed로 기록됐다. 전체 브랜치 위험 중심 리뷰와 마지막 중첩 요청 수정의 부분 재리뷰에서도 남은 Critical/Important 항목은 없었다. 리뷰는 코드 검토이며 테스트 실행의 대체 증거로 쓰지 않는다.

## 4. 데이터 불변성·상태·통계 계약

`EssaySubmission`은 문항별 증가 순번으로 명시 확인을 기록한다. 기존 `is_submitted`는 과거 표시의 의미를 유지한다. 새 Practice는 최근 확인한 버전을 우선하며, 확인 기록이 없을 때만 기존 표시의 선택 규칙을 사용한다. 새 초안·복원·다른 버전 재제출이 과거 버전이나 기존 Practice snapshot을 수정하지 않는다.

`ApplicationState`는 신규 지원 건의 기준 상태와 수동/legacy override를 분리한다. override가 없을 때만 `(event_date, created_at, id)` 순 이벤트를 재생한다. 수동 단계·상태는 이벤트 편집/삭제가 덮어쓰지 않는다. 기존 데이터는 현재 상태를 legacy로 보존하며 `POST /track/applications/{id}/state-from-events`에서 명시 전환한다.

각 전형의 `도달 = 통과 + 탈락 + 대기`, `통과율 = 통과 / (통과 + 탈락)`을 적용한다. 미확정·대기는 분모에 넣지 않으며 확정 결과가 없으면 통과율은 null이다. 보류는 호환용 pending에 포함하되 hold로 분리해 표시한다. 지원일이 없는 건은 `undated_count`이고, `applied_monthly`에 등록일을 대신 넣지 않는다. 기존 `monthly`는 호환 필드로 남긴다.

잠금은 Application→EssayItem 순서를 사용한다. 독립 PostgreSQL 트랜잭션의 URL 생성·버전 추가·새 문항 sync 경합 검증이 포함된다. UI 병합은 서버 불변성을 대신하지 않으며 서버의 소유권 검사는 별도로 유지한다.

## 5. Apply·Extension·팀 이식

새 API는 `PATCH /track/events/{id}`, `POST /track/applications/{id}/state-from-events`, `POST /track/versions/{id}/submit`이다. 기존 `/track/sync`의 경로·필드·생략 시 `submitted=true` 계약은 유지한다. 생략 요청은 명시적 제출 확인 이력으로 승격하지 않는다. 신규 Apply/확장은 초안은 false, 사용자가 제출했다고 확인한 경우만 true를 반드시 보낸다.

Apply 전체, 실제 채용 사이트 자동입력, 실제 팀 로그인 전달부는 이번에 새로 구현하지 않는다. 답변 전달은 사용자의 동의를 얻은 Apply 클라이언트의 책임이다. 확장 검증은 Chrome/API 대역 결과이며 실제 설치·권한·외부 사이트 확인으로 표현하지 않는다.

[팀 저장소 이식 안내](../integration/team-repository-handoff.md)는 2026-11-06 원격에서 다시 확인한 팀 `feature/frontend`의 SHA [`ec7b279eda87b5dd49beadff453947aa32309e62`](https://github.com/seungxa/26-2_CapstoneProject/commit/ec7b279eda87b5dd49beadff453947aa32309e62)를 기준으로 파일·라우트·API·CSS·모델 자산·테스트 순서를 제시한다. 이전 `cc7b5b2`에서1커밋 전진했고, 2026-11-05 20:37:54 KST의 Profile/JSON export 변경이다. 변경 파일은 App.css·새 lib/archiveFields.ts·Profile.tsx 세 개뿐이다. App·로그인·라우팅·Apply·package/lock은 이 커밋에서 바뀌지 않았다. 팀 로그인·회원가입·Profile·Dashboard·공통 UI·단일 Router를 유지하며 JobSeeker `App.tsx` 전체는 옮기지 않는다.

최신 lock도 팀 React19.3.1/Router8.4.0/Vite8.3.4/TypeScript6.0.3/Supabase JS2.118.0이며 Node22.22.0 이상이 필요하다. JobSeeker는 React18.3.1/Router6.30.6/Vite6.4.4다. 버전 차이, 전역 CSS와 새 archive 스타일, 하위 라우트, MediaPipe 자산 경로가 예상 충돌이다.

최신 Profile은 기존 `basic/education/sections` 대신 **`profiles.archive`**를 조회·저장한다. `schemaVersion:'1'`의 profile 및7개 그룹과 명시적 `jobseeker-archive.json` 내보내기를 제공하는 클라이언트 코드를 확인했다. 실제 DB 컬럼·기존 행 변환·RLS는 확인하지 않았고 해당 SQL도 최신 tree에 없다. 이 식별 정보 포함 프로필 JSON과 익명 미디어 검증 JSON을 혼용하거나 전체 프로필을 동의 없이 Track/코칭으로 보내지 않는다. Apply 페이지는 여전히 placeholder이며 실제 JSON 수신·자동입력·확장은 확인하지 못했다.

팀의 실제 Supabase 서명 설정·archive DDL/기존 데이터 호환·RLS·Storage·테이블 충돌·Apply 구현 위치·빌드 기준선은 실제 이식 전에 확인해야 한다. 팀 앱 설치·빌드·실행이나 저장소 변경은 하지 않았으며 최신 원격 소스 검토만 수행했다.

## 6. 인증·DB 활성화와 롤백 경계

인증은 기본 활성화한다. 로컬 테스트만 명시적으로 우회하며 운영 환경에서 우회를 지정하면 시작을 거부한다. HS256/JWKS 중 서버 설정으로 선택하고 고정 issuer·audience·알고리즘·만료·UUID 사용자 ID를 검증한다. JWKS 주소는 토큰이 지정한 URL에서 선택하지 않는다. 팀의 실제 서명 키 방식이 확인됐다는 뜻은 아니다.

웹 API 클라이언트는 API 주소·토큰 제공자·인증 오류 처리를 주입한다. 팀 Supabase 클라이언트가 갱신의 단일 소유자이고 GET만 제한적으로 재시도한다. 저장·업로드는 자동 재전송하지 않는다. 로그아웃/사용자 변경은 진행 요청·응답과 탭 메모리를 무효화하며 서버 녹음 삭제를 호출하지 않는다.

검증 DB는 실제 PostgreSQL/PostgREST이며 관리형 Supabase가 아니다. API JWT A/B 사용자 필터와, `NOSUPERUSER NOBYPASSRLS` 비소유자의 PostgREST/RLS를 구분한다. auth/storage 최소 SQL 대역은 실제 Auth·Storage 서비스 검증을 대신하지 않는다.

기존 migration은 수정하지 않는다. 새 Track 상태/제출 이력 및 버전 가드 migration은 이 릴리스의 시작 전제이고 Stage 2 활성화 플래그와 구분한다. Stage 2 분류·스냅샷은 nullable 추가 구조를 보존하며 기능 off/on과 이전 앱 복귀 시 데이터를 지우지 않는 롤백을 검증한다. 실제 운영 SQL 적용은 수행하지 않는다. 절차는 [롤아웃 안내](../practice-insights-rollout.md)와 [PostgreSQL 검증](../postgresql-validation.md)을 따른다.

## 7. 비언어적 관찰·코칭 품질·성능

관찰은 탭 메모리에만 보관하고 새로고침하면 사라진다는 안내를 제공한다. 파일 보관은 사용자가 명시적으로 익명 집계 JSON을 내보낼 때만 한다. 내보낸 파일은 앱에서 회수할 수 없다. 전사문·토큰·사용자/답변 ID·원본 프레임·랜드마크·시계열·캘리브레이션 계수는 내보내지 않는다. 편집 중이거나 저장 녹음과 전사문이 맞지 않으면 해당 음성 텍스트 지표의 내보내기를 막는다.

Gaze G1/G2는 면접 평가에서 비활성화한다. `(max(relative e50)-min(relative e50))/median(relative e50)` 반복 참고값은 조건이 같은 유효 complete 결과가3개 이상일 때만 계산하며 H2 전체 인증으로 쓰지 않는다. 실패한 complete는 분모에 남기고 invalid/aborted/error는 사유와 함께 별도 기록한다. 정확도 개선·합격 가능성·감정·자신감은 추정하지 않는다.

다섯 피드백 층은 항목별 짧은 코멘트→답변 종합→면접 전체 스크립트→다음 행동→유형별 개선 구성안이다. 행동을 항목마다 반복하지 않고 전체 답변의 서로 다른 근거/영향 범위로 종합한다. 지문 없는 legacy 보고서는 보존하되 현재 종합 근거로 사용하지 않고 자동 재분석하지 않는다. 실제 AI 코칭 품질은 human rubric의 `not_evaluated` 상태다.

외부 유료 API 호출은 **0회**로 유지한다. 기존 모델 전송 범위를 넓히지 않고 추가 분석 호출·조회 시 자동 재분석을 만들지 않는다. 로컬 AI 대역의 각 viewport 시나리오 호출은 최종 로컬 HTTP E2E에서도 coach2/debrief1/generate0이었다. 펼치기·새로고침·기존 꼬리질문·재연습 재사용이 호출을 늘리지 않음을 검증했다. 실제 클라우드 토큰 비용 측정은 하지 않았다.

## 8. 과거 실행 결과와 현재 한계

복구한 2026-11-05 보고서의 가장 최근 기록은 backend384passed, unit129passed, build통과, 실제 격리 PG/PostgREST17passed, Track→Practice UI2passed, Practice 수정 회귀20passed, 로컬 AI 전송2passed, media browser2passed, Gaze1passed이다. 이들은 서로 다른 범위·실행의 결과이며 합산해 전체 E2E 통과 수로 사용하지 않는다. 이전의 전체 E2E 최종 실행은 결과 로그가 사라져 종료 결과를 확인하지 못했으므로 **결과 미확인**이다.

서로 다른 탭에서 문항을 삭제한 경우 현재 상세 화면의 보수적인 병합에 그 문항이 남을 수 있다. 전체 페이지를 다시 불러오면 서버 상태를 반영한다. 서버 이력은 유지되지만 완전한 다중 탭 실시간 동기화를 제공하는 것은 아니다.

실제 Supabase 클라우드 Auth/Storage/RLS, 실제 팀 토큰 서명 설정, 설치 Chrome 확장과 외부 채용 사이트, 실제 모바일 기기, 사람의 마이크·웹캠·Gaze3회 측정, 실제 AI 품질은 이번 자동 검증으로 완료 표시하지 않는다. 원래 실행기 작업·사용자 DB·녹음·비밀 설정은 읽거나 수정하지 않는 범위를 유지한다.

## 9. 사람이 진행할 최소 절차

사람이 수행할 확인은 [미디어 검증 안내](../media-validation.md)의 독립 pilot 실행 절차를 사용한다. 운영 계정·실제 자소서 대신 테스트 입력을 사용하고 카메라/마이크 권한은 사용자가 직접 허용한다.

1. 조용한 환경에서 약30초 답변을 녹음하고 전사문·말 빠르기·침묵/추임새 후보를 직접 대조한다. 잡음 환경에서 한 번 더 실행하고 관찰 부족/불안정 안내가 나오는지 확인한다.
2. 얼굴 정면→프레임 밖→좌우 회전/숙임을 수행한다. 조명·안경·카메라 높이는 한 조건씩 바꾸고 감정/자신감 평가가 표시되지 않는지 확인한다. 필요한 집계만 명시적으로 JSON 내보낸다.
3. [Gaze 실측 프로토콜](../research/2026-11-04-gaze-protocol.md)에 따라 같은 조건에서 각각 새 캘리브레이션으로3회 측정한다. 실패/중단도 기록하고 조건이 다른 결과는 한 그룹에 섞지 않는다.
4. 테스트 지원 건의3문항 중 과거 버전을 제출본으로 확인해 Practice를 시작한다. 이후 Track을 바꿔도 기존 면접 기준 자료가 유지되는지 직접 확인한다. 실제 팀 로그인/확장/채용 사이트 검증은 팀 이식 준비가 끝난 뒤 별도로 수행한다.

JSON 비교는 `cd backend && .venv/bin/python -m evals.validation.compare --input <결과1.json> --input <결과2.json> --input <결과3.json> --out <새_비교_디렉터리>`로 실행한다. 분석 결과만으로 G1/G2를 활성화하지 않는다. 유료 모델 품질 평가는 사용자가 별도로 동의한 후 합성 사례와 rubric으로 진행해야 한다.

## 10. 자율 판단과 비용

- 사용자 승인에 따라 파일 소유권을 나눠 병렬 작업했다. 공유 모델·API·스키마는 총괄이 통합했다. 경계를 잘못 나누면 충돌 위험이 있어 전체 테스트와 독립 리뷰로 확인한다.
- 초기 의존성 재사용 뒤 Vite 캐시 쓰기가 읽기 전용 링크에서 거부되어 프런트엔드 의존성을 전용 폴더에 복사했다. 버전 변경은 없으며 비용은 약136MB 디스크다. 백엔드 추가 패키지는 전용 venv에만 설치했다.
- 새 Track migration2개는 이번 릴리스의 필수 시작 전제로 판단했다. Stage2 비활성화와 별개라서 배포 전 적용을 누락하면 서버가 시작하지 않는다. 분류 rollback은 데이터 삭제 없이 플래그로 수행한다.
- 사라진 `/tmp` 결과를 현재 검증으로 간주하지 않았다. 영속 Worktree에서 복원·독립 대조·새 실행을 수행했다. 과거 보고서는 감사 기록으로 보관한다. 남은 위험은 재현되지 않은 환경 차이다.
