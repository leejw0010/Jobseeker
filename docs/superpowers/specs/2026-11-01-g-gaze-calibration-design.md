## 1. 현재 구조와 제약 (코드로 확인)

**검출 (`web/src/video/detector.ts`)**
- MediaPipe Face Landmarker(`@mediapipe/tasks-vision` 1.1.1), `VIDEO` 모드, 얼굴 1개, GPU로 만들지 못하면 CPU.
- 모델 `face_landmarker/float16/1`은 특징점 478개를 낸다.
  - 홍채: 오른쪽 중심 468(테두리 469~472), 왼쪽 중심 473(474~477).
  - 눈꼬리 33·133 / 362·263, 눈꺼풀 159·145 / 386·374. 좌우는 피사체 기준이다.
- 지금은 `faceLandmarks[0]`만 쓴다. 표정 계수·변환 행렬은 꺼져 있고 `setOptions()`로 켤 수 있다. G는 켜지 않는다(결정 1·2).

**반복과 D 지표 (`useFaceAnalysis.ts`, `metrics.ts`)**
- 메인 스레드에서 `setInterval(tick, 250ms)`로 돈다. 탭이 가려졌거나 영상이 준비되지 않으면 건너뛴다.
- 표본마다 D가 상태(`in`/`edge`/`none`)와 고개 비율을 낸다. 답변 구간 요약은 탭 메모리에만 둔다.
- 카메라 스트림은 마이크와 따로이고 640×480을 요청한다. 미리보기는 좌우 반전·`object-fit: contain`이다.

**화면**

**테스트**

**지킬 결정**

## 2. 목표와 하지 않는 것

목표
- G1: 카메라 **렌즈**를 보는지 `toward` / `away` / `unknown`으로 추정한다. 화면 위쪽(질문 등)을 보는 것과 렌즈를 보는 것을 구별할 수 있는지부터 **시험**하고, 구별되지 않으면 한계로 보고하고 G1을 쓰지 않는다.
- G2: 화면 영역(`question` / `ui` / `offscreen` / `unknown`)을 개인별 화면 좌표 회귀로 추정한다. 영역은 DOM 요소의 실제 위치·크기로 정하고, 나중에 아바타 영역을 더할 수 있게 한다.
- 정확도는 **보정·모델 선택에 쓰지 않은 위치**로만 잰다. 불확실하면 `unknown`(사유 포함)이나 "사용 안 함"으로 두고, 오차가 영역보다 크면 그 영역을 봤다고 하지 않는다.
- 회고에 답변별 시선 시간·비율, 판정 불가 시간, 변화 구간, 타임라인, 보정 품질을 보인다.

하지 않는 것
- 감정·자신감·집중도·정직함·면접 역량 추정, 점수화. 렌즈를 덜 봤다고 회피로 해석하지 않는다.
- 아바타·TTS·AI 면접관, 녹화 재생(C 전).
- 새 의존성, D 판정 기준·표본 주기 변경, 두 번째 카메라 스트림·검출기.
- 모바일(결정 9). 실제 면접 중 쓰는 기능.

## 3. 전체 구조

```
카메라 스트림(기존 1개) → 검출기(기존 1개) → tick(프레임당 검출 1회)
   ├─ D: 250ms 격자에 맞춘 표본만 받아 지금과 같은 요약
   └─ 프레임 구독(frame tap) → G 특징(4절)
        ├─ G1 렌즈 분류기(5절) → toward / away / unknown
        └─ G2 화면 회귀(6절) → 예측점 → 영역 판정(9절)
             └─ 평활·판정(8절) → 실시간 상태 · 답변 타임라인(11절)
```

순수 계산 모듈은 `web/src/video/gaze/`에 둔다. 0단계 시험과 본 구현이 같은 모듈을 쓰며, 0단계에 계산 테스트와 함께 만든다.

|---|---|

## 4. 입력 특징 (결정 1·2, 승인)

- 원본(좌우 반전 전) 프레임 좌표를 쓴다. 정규화 좌표를 **픽셀 좌표(x·W, y·H)로 바꾼 뒤** 거리·각도를 계산한다(4:3이 아니어도 비율이 틀어지지 않게).
- **눈 좌표계:** 두 눈꼬리 중점이 원점, 눈꼬리 방향이 x축, 눈 폭이 단위. 고개를 갸웃해도 따라 돈다.
- **홍채 위치 `ex, ey`:** 홍채 중심(468·473)을 눈 좌표계로 옮겨 두 눈 평균.
- **눈 뜬 정도 `open`:** 눈꺼풀 거리 / 눈 폭을 2단계 기준값으로 나눈 비율. 렌즈는 화면보다 위에 있어 렌즈를 볼 때 윗눈꺼풀이 더 올라가므로, G1의 입력으로도 쓴다.
- **고개 방향 `hx, hy`:** D와 같은 특징점 비율. 부호와 크기는 보정이 정한다(D-17의 축 규약 문제를 피함).
- **얼굴 위치·크기:** 두 눈 중심 위치, 눈 사이 거리 / 프레임 너비. 모델 입력이 아니라 "보정 때와 자세가 달라졌는지" 판정에만 쓴다.
- **유효성:** 눈 점이 프레임 안(여유 0.01), `open` ≥ 0.5, 두 눈 홍채 위치가 보정 때 흩어짐에 비해 크게 어긋나지 않음.

시선 판정은 언제나 홍채 특징을 쓴다. 고개 방향은 보조 입력이며, 고개 방향만으로 시선을 정하지 않는다.

## 5. G1 — 렌즈 응시 분류기 (결정 4, 개정)

**왜 따로 두는가**
- 화면 좌표 회귀로 렌즈 위치를 추정하면 보정 범위 밖으로 외삽해야 한다.
- 노트북 카메라는 화면 위 가장자리에 붙어 있어, 렌즈와 화면 위쪽 가운데가 각도로 가깝다.
- 그래서 렌즈 응시는 **직접 모은 양성·음성 표본으로 학습한 별도 분류기**로 판정한다.

**학습 표본** — 같은 보정 세션에서 모은다(6절)
- 양성: 렌즈를 보는 표본.
  - 정면 2번(2단계).
  - 고개를 살짝 왼쪽·오른쪽으로 돌린 채 렌즈 응시(4단계 b).
- 음성: 화면을 보는 모든 표본.
  - 9점, 가운데 점을 보며 고개를 움직인 표본.
  - **화면 위쪽 띠의 어려운 음성:** 뷰포트 위 2% 높이의 35%·50%·65% 지점(4단계 c). 9점의 위쪽 가운데(50%, 8%)도 포함한다.

**입력과 모델**
- 표준화한 `[ex, ey, hx, hy, open]`.
- L2 정규화 로지스틱 회귀를 TypeScript로 직접 구현한다(뉴턴법, 특징 5개 + 절편). 양성이 적으므로 클래스 가중치를 맞춘다.
- 고개가 돌면 눈이 반대로 돌아 렌즈를 보는 선형 보상 관계를 선형 결정 경계로 담을 수 있다.
- 더 복잡한 모델은 0단계 결과가 선형으로 부족할 때만 검토한다.

**임계값** — 보수적으로 정하고, 사이는 `unknown`
- 묶음 단위 교차 검증으로 정한다. 응시 한 번(지점·자세 하나)에서 나온 연속 프레임은 한 묶음이고, 한 묶음은 학습과 검증에 나뉘어 들어가지 않는다.
- 각 묶음을 뺀 모델로 그 묶음의 확률 `p`를 구한다.
  - `τ_hi = max(0.8, t₁)`. `t₁`은 위쪽 띠 음성 중 `p ≥ t₁`이 5% 이하가 되는 가장 작은 값.
  - `τ_lo = min(0.2, t₀)`. `t₀`는 렌즈 양성 중 `p ≤ t₀`가 5% 이하가 되는 가장 큰 값.
  - 그래서 언제나 `τ_lo ≤ 0.2 < 0.8 ≤ τ_hi`이고, 두 클래스가 잘 갈려도 가운데 `unknown` 띠가 남는다.
- 판정: `p ≥ τ_hi`면 `toward`, `p ≤ τ_lo`면 `away`, 그 사이는 `unknown`.
- 분포 밖 검사: 현재 특징이 학습 표본 전체에서 멀면(학습 분포 기준 마할라노비스 거리가 학습 표본의 99번째 백분위를 넘으면) 확률과 관계없이 `unknown`.

**구별 가능성 판정** — 0단계에서 이 판정 자체를 시험한다
- **판정에는 학습에도 임계값 선택에도 쓰지 않은 별도 응시(7절 5단계)만 쓴다.**
  - 새로 모은 렌즈 응시: 정면, 고개 왼쪽, 고개 오른쪽.
  - 새로 모은 위쪽 띠 응시: (40%, 5%), (50%, 5%), (60%, 5%). (50%, 5%)가 화면 위쪽 가운데다.
- 이 응시들로 다음을 계산한다.
  - 렌즈 대 위쪽 띠 AUC.
  - `τ_hi`에서 렌즈 응시가 `toward`로 나온 비율(정면, 고개 돌림 따로).
  - 위쪽 띠 응시가 `toward`로 잘못 나온 비율.
- 교차 검증 확률은 임계값을 정하고 모델 상태를 보는 진단용이다. 정확도로 보고하지 않는다.
- 13절 기준에 못 미치거나 결론이 나지 않으면 G1은 끄고(판정은 언제나 `unknown`), **"화면 위쪽과 렌즈를 구별할 수 없음"**으로 끄고, 그 사실을 보고·화면에 밝힌다. 이때 렌즈를 본 시간은 G2의 `offscreen` 또는 `unknown`에 들어간다고 회고에 적는다.

## 6. G2 — 화면 좌표 회귀 (결정 3, 검증 조건부 승인)

**출력**
- 보정할 때의 뷰포트 CSS 픽셀 좌표 `p = (X, Y)`.

**후보 모델** — X·Y마다 따로, 표준화한 특징에 릿지(절편은 벌점 없음)
- M1(선형): `[1, ex, ey, hx, hy]`
- M2(정규화 2차): M1 + `[ex², ey², ex·ey]`

**선택** — 누출 금지
- 묶음 단위 교차 검증을 쓴다. 묶음은 보정 응시 하나(9점의 각 점, 고개 자세 각각)이고, 연속 프레임을 학습과 검증에 나누지 않는다.
- λ ∈ {0.01, 0.1, 1, 10}와 M1/M2를 같은 교차 검증으로 고른다. M2는 오차 중앙값이 M1보다 15% 이상 작을 때만 고른다.
- **최종 정확도는 보정·선택에 전혀 쓰지 않은 검증 위치로만** 잰다(7절). 교차 검증 오차는 선택에만 쓰고 정확도로 보고하지 않는다.
- 거리 기반 비모수 방법은 점 9개로는 안정적이지 않아 쓰지 않는다.

**질문 영역 크기 조사 (결정 6, 검증 조건부 승인)**
- 0단계에서 높이 32px(지금 한 줄), 120px, 240px인 가상 질문 패널을 실제 `.runner-q` 위치에 띄워 판정 적중률을 잰다.
- 결과로 "질문 영역 판정이 쓸모 있으려면 패널이 얼마나 커야 하는지"를 보고한다.
- 패널을 키우는 화면 변경은 그 결과를 보고 따로 결정한다. 그 전에는 영역이 오차보다 작으면 판정하지 않는다(9절).
- 지금의 작은 질문 글이 맞지 않는다고 시선 기능 전체를 포기하지 않는다. 판정이 쓸모 있는 **최소 패널 크기**를 보고한다.

**보고는 두 가지를 함께 한다**
- 화면 좌표 오차(`e50`·`e80`).
- 실제 영역 판정 성능(7절): 영역을 볼 때 맞게 판정한 비율, `unknown` 비율, 다른 영역으로 잘못 판정한 비율.

## 7. 보정 화면과 검증

**표시 방식**
- 진행 화면 위 오버레이로 띄우고, 전체 화면 모드는 쓰지 않는다(뷰포트가 바뀌면 보정이 무효).
- 카메라 미리보기는 오버레이 밑에서 계속 재생하되 보이지 않는다.
- 점이 나타난 뒤 0.7초는 버리고 1초(4단계 각 자세는 2초) 수집한다. 단계마다 "준비되면 시작".

| 단계 | 내용 | 통과 기준(잠정) |
|---|---|---|
| 1 카메라 준비 | 권한·검출·해상도·눈 폭(px)·위치·조명 안내 | 2초 중 유효 ≥ 90%, 눈 폭 ≥ 20px |
| 2 렌즈 응시(정면) | 1.5초씩 2번, 사이에 가운데 점 1초. `open`·자세 기준값도 잰다 | 두 번의 특징 평균 차이 ≤ 흩어짐의 2배, 유효 ≥ 80% |
| 3 화면 9점 | 8%·50%·92% 격자, 가운데부터 뱀 순서. "고개는 그대로, 눈으로" | 점마다 유효 ≥ 8개, 실패한 점은 끝에 다시(최대 2번), 7점 미만이면 실패 |
| 4a 고개 움직임 | 가운데 점을 보며 정면·왼쪽·오른쪽·위·아래 | 자세마다 유효 ≥ 8개 |
| 4b 고개 돌린 렌즈 응시 | 고개 살짝 왼쪽·오른쪽으로 돌리고 렌즈 | 자세마다 유효 ≥ 8개 |
| 4c 위쪽 띠 | 뷰포트 위 2% 높이의 35%·50%·65% 지점 | 점마다 유효 ≥ 8개 |
| 5 검증(모두 처음 보는 위치, 학습·임계값 선택에 쓰지 않음) | 25%·75% 격자 4점, 고개를 왼쪽으로 돌린 채 (30%, 50%)·오른쪽으로 돌린 채 (70%, 50%), 위쪽 띠 (40%, 5%)·(50%, 5%)·(60%, 5%), 렌즈(정면·고개 왼쪽·오른쪽, 새로 수집) | 아래 지표 |
| 6 질문 패널 | 높이 32·120·240px 가상 패널의 가운데 | 영역 판정 성능 |

- 예상 소요는 약 1분 20초.
- 보정을 건너뛰어도 면접 연습·STT·D 지표는 그대로다. 결과 화면에서 다시 보정 / 이대로 사용 / 시선 분석 끄기를 고른다.

**검증 지표** — 5단계 표본만 사용
- G2 좌표:
  - 화면 오차 `e50`·`e80`(px, 뷰포트 너비 %).
  - 고개를 돌린 상태의 오차((30%, 50%)·(70%, 50%)).
- G2 영역 판정 성능(패널 높이별):
  - 패널을 볼 때 `question` 적중, `unknown`, 다른 영역 비율.
  - 패널 밖 검증점에서 `question` 오판, `ui` 정답, `unknown` 비율.
  - 패널이 `2·e80`보다 작아 판정하지 않았는지.
- G1(처음 보는 응시만):
  - 렌즈 대 위쪽 띠 AUC.
  - 렌즈 `toward` 비율(정면, 고개 돌림).
  - 위쪽 띠·화면 검증점에서 `toward` 오판 비율.
  - 교차 검증 AUC는 진단용으로만 함께 적는다.
- 공통: 유효 표본 비율, 안정성(2단계 두 번의 차이, 검증 응시 중 예측 흩어짐).

**품질 등급**(잠정, 결정 10)
- G2:
  - 사용 안 함: 유효 < 60%, 또는 `e50` > 너비 15%, 또는 9점 중 7점 미만.
  - 낮은 신뢰: `e50`이 너비 8~15%, 또는 유효 60~80%.
  - 보통: 그보다 좋음.
- G1은 5절 구별 가능성 판정과 검증 지표로 따로 켜고 끈다.
- 실제 웹캠 측정 전에는 이 기준값이 맞는지 모르므로 한 상수 파일에 모아 두고 조정한다.

## 8. 실시간 판정

표본마다 아래 순서로 처리한다. 앞에서 걸리면 `unknown`과 사유를 남긴다. 판정 불가 표본은 어떤 응시 범주에도 넣지 않는다.

1. 보정 유효성(9절 뷰포트 변화 없음, 등급) → `calibration_stale`
2. 얼굴 미검출 → `no_face`
3. 눈 점이 프레임 밖 → `eyes_outside`. D의 `edge`라도 눈이 안이면 계속한다
4. `open` < 0.5 → `eyes_closed`
5. 두 눈 홍채 불일치 → `eyes_unreliable`
6. 고개 방향이 보정 범위(3·4단계 최소~최대, 여유 10%) 밖 → `head_out_of_range`
7. 얼굴 크기 변화 > 15% 또는 위치 이동 > 프레임 10% → `position_changed`. 5초 넘게 이어지면 다시 보정 안내(카메라 거리 변화 포함)
8. 평활: 최근 0.6초 유효 표본의 G2 예측 중앙값, G1 확률 평균
9. 판정:
   - G1: 5절 임계값.
   - G2: 여유값 `m = e50`.
     - `question`: 질문 영역을 `m`만큼 줄인 사각형 안. 영역이 `2·e80`보다 작으면 판정하지 않음.
     - `ui`: 뷰포트 안이면서 등록 영역을 `m`만큼 넓힌 사각형 밖.
     - `offscreen`: 뷰포트를 `m`만큼 넓힌 사각형 밖.
     - 경계 띠는 `ambiguous`.
   - 상태 바뀜은 0.2초 이상 이어질 때만 받아들인다.

**회고용 하나의 대상** `camera | question | ui | offscreen | unknown`
- G1이 켜져 있고 `toward`면 `camera`, 아니면 G2.
- G1이 `toward`인데 G2가 화면 안 영역이면 서로 모순이므로 `unknown(ambiguous)`.

**고개·눈 분리**(진단·검증용)
- G2 예측을 눈 기여 `W_eye·(e − e0)`와 고개 기여 `W_head·(h − h0)`로 나누고, 각 기여가 `e50`을 넘는 방향으로 "눈 왼쪽", "고개 오른쪽" 등을 붙인다.
- "고개 왼쪽·렌즈 응시"는 4단계 b로 학습·검증한다.

**좌우 표기**
- 사용자·화면 기준이다. 보정이 원본 프레임 좌표와 실제 화면 좌표를 직접 이으므로, 미리보기 반전이 판정을 뒤집지 않는다.
- 가짜 검출기는 "사용자가 자기 오른쪽을 보면 원본 프레임에서 홍채 x가 작아진다"(D `edgeLabel`과 같은 규약)를 따른다.

## 9. 화면 영역과 보정 유효성

**영역 등록부**
- `registerGazeRegion(id, element, priority)`, React는 `useGazeRegion("question")` ref로 등록한다.
- 지금은 `question` 하나. `ui`는 뷰포트 중 등록 영역이 아닌 곳이다. `avatar`는 나중에 같은 방식으로 더한다.
- 위치는 표본마다 `getBoundingClientRect()`로 다시 읽는다. 스크롤·레이아웃 변화는 보정을 무효로 만들지 않는다.

**보정 무효화**
- 보정 때 `innerWidth`·`innerHeight`·`screenX`·`screenY`·`devicePixelRatio`·`visualViewport`(배율·위치)를 기록한다.
- 값이 바뀌면(창 크기·창 위치·모니터·확대/축소·전체 화면) `calibration_stale`이 되고 "다시 보정이 필요해요"를 띄운다.
- `screenX`가 늘 0인 브라우저 설정에서는 창 이동을 알 수 없다(한계).

## 10. 표본 주기와 성능 (결정 7, 검증 조건부 승인)

**후보와 측정**
- 초당 10회와 15회는 **후보**다. 기본값은 0단계 측정으로 정한다.
- 시선을 끄면 지금처럼 초당 4회(카메라 분석만 쓰는 모드 유지).
- 잴 것:
  - 실제 MediaPipe 추론 시간(`detectForVideo` 앞뒤, p50·p95).
  - 실제 표본 주기.
  - 메인 스레드 응답성(`setTimeout` 지연 오차 p95, 지원 시 `longtask` 수).
  - 메인 스레드 점유율(추론 시간 × 주기).
  - 유효 표본 비율.
  - 글 답변 입력 중 지연.
- CPU 사용률은 웹 API로 알 수 없어 OS 작업 관리자 값을 수동으로 적는다.

**D 호환**
- D는 250ms 격자의 각 칸에서 처음 오는 표본만 받는다. 평균 초당 4회이고 기준·문구가 같다.
- 자동 테스트: 같은 가짜 표본 순서를 초당 4·10·15회로 넣었을 때 D 요약이 같은지(격자 한 칸 오차 안).
- 실제 웹캠: 카메라만 / 시선 켬 상태에서 D 검출 비율 비교.

**적응 정책**(잠정)
- 한 단계 내리는 조건(하나라도): 점유율 > 25%, 최근 10초 긴 작업 ≥ 2, 지연 오차 p95 > 50ms.
- 10초 괜찮으면 한 단계 올린다. 목표를 넘지 않고, 4회 아래로는 내리지 않는다.
- 높은 주기를 강제하지 않는다.

**STT·녹음 흐름은 바꾸지 않는다.**

## 11. 면접 화면과 회고

**진행 화면** (`CameraPanel`, 카메라가 켜진 뒤)
- 시선 분석 동의(별도) → 보정 시작 / 다시 보정 / 보정 지우기.
- 상태: 미보정 / 보통 / 낮은 신뢰 / 사용 안 함 / 다시 보정 필요. G1을 쓸 수 없으면 "렌즈 응시는 구별할 수 없음"으로 따로 표시한다.
- 실시간 한 줄 상태(숨기기 가능). 답변 중에는 보정을 시작하지 못한다.
- 시선 분석을 켜지 않으면 지금 화면 그대로다.

**회고** (`GazeReport`)
- 답변별: 답변 시간, 시선 분석 시간, 대상별 시간·비율(분모는 판정한 시간), 판정 불가 시간과 주요 사유, 변화 횟수(0.3초 이상 이어진 대상 사이), 타임라인 막대(색·무늬 + 글 대체).
- 보정 품질: G2 `e50`·등급, G1 사용 여부와 렌즈 응시 일치율, 판정하지 않은 영역, 사용한 표본 주기.
- 점수는 매기지 않는다.

**데이터 구조** (탭 메모리, 좌표·특징점 없음)

```ts
type GazeTarget = "camera" | "question" | "ui" | "offscreen";
type GazeUnknown = "no_face" | "eyes_outside" | "eyes_closed" | "eyes_unreliable" | "head_out_of_range"
                 | "position_changed" | "ambiguous" | "calibration_stale";
type GazeRun = { startMs: number; endMs: number; target: GazeTarget | null; unknown?: GazeUnknown };
type GazeSegment = {
  anchor: { perfMs: number; epochMs: number };  // 답변 시작 순간(C의 녹화 시각과 맞출 기준)
  answerMs: number; analyzedMs: number;
  byTarget: Record<GazeTarget, number>; unknownMs: number; unknownBy: Partial<Record<GazeUnknown, number>>;
  transitions: number; runs: GazeRun[]; rates: number[];
  calibration: { id: string; g2Grade: "ok" | "low"; e50Px: number; e50Pct: number;
                 g1: "on" | "off_inseparable" | "off_quality"; unresolvable: string[] };
};
```

  - README 카메라 절, 결정 D-21.

## 13. 0단계 — 실현 가능성 시험 (전체 구현 전)

**검증할 가정**
- H1: 실제 웹캠에서 렌즈 응시와 화면 위쪽 가운데 응시를 G1로 구별할 수 있다.
- H2: G2가 보정에 쓰지 않은 위치에서 영역 판정에 쓸 만한 오차를 낸다. 질문 패널은 얼마나 커야 하는지도 본다.
- H3: 초당 10·15회가 메인 스레드를 해치지 않고 D와 호환된다.

**만드는 것** (개발 전용)
- `VITE_GAZE_LAB=true`인 개발 서버에서만 열리는 "시선 실험실" 화면(프로덕션 번들에 없음, 확인함).
- 기존 `useFaceAnalysis`의 스트림·검출기를 그대로 쓴다. 필요한 것은 프레임 구독 하나다(본 구현에도 필요).
- 계산 모듈 `features`·`regression`·`lens`·`sampler`는 계산 테스트와 함께 만든다(본 구현에서 그대로 쓴다).
- 화면은 7절 순서(약 1분 20초)에 더해 다음을 안내한다.
  - 거리 변화: 보정 뒤 약 10cm 앞으로, 이어서 뒤로. 각각 검증 4점 + 렌즈.
  - 질문 패널 3종(32·120·240px).
  - 주기 시험: 초당 4·10·15회 각 20초 가운데 응시 + 글 입력 20초.
- 끝나면 **집계 지표만** 보여 주고 복사할 수 있다. 프레임·특징점·좌표·표본은 보여 주지도 복사하지도 않는다. 화면을 떠나면 지운다.

**시험 절차** (사용자, 실제 노트북 내장 웹캠, 평소 거리·조명)
- 3번 반복한다(매번 새로 보정). 가능하면 안경·어두운 조명으로 1번 더.
- 화면 크기·뷰포트·카메라 위치를 함께 적는다.

**판정 기준** — 1단계로 넘어갈지 정하는 실험 기준이다.
- 통과해도 실제 사용에 충분한 신뢰성을 보였다는 뜻이 아니다.
- AUC·오차 기준·"3번 중 2번" 결과를 제품의 정확도 보장으로 쓰거나 보고하지 않는다.
- 신뢰성은 1단계 뒤 더 많은 사람·기기·조건에서 잰 결과로만 말한다.

| 가정 | 통과 | 실패(그 기능을 빼고 한계로 보고) |
|---|---|---|
| H1 렌즈 대 화면 위쪽 | 3번 중 2번 이상, **처음 보는 응시만으로**: AUC ≥ 0.85, 렌즈 응시(정면) `toward` ≥ 60%, 고개 돌린 렌즈 응시 ≥ 40%, 위쪽 띠 오판 ≤ 10% | 3번 중 2번 이상: AUC < 0.75, 또는 렌즈 `toward` < 30%, 또는 위쪽 띠 오판 > 20% → G1 끔(`unknown`) |
| H2 화면 회귀 | 3번 중 2번 이상: 처음 보는 4점 `e50` ≤ 너비 8%, `e80` ≤ 12%, 고개 돌린 오차 ≤ 정면의 1.5배, 유효 ≥ 80%. 반복 간 `e50` 차이 ±30% 이내 | 3번 중 2번 이상: `e50` > 너비 15% 또는 유효 < 60% |
| H2 질문 패널(영역 판정 성능) | 적중률 ≥ 80%이고 패널 밖 처음 보는 점의 `question` 오판 ≤ 10%인 **가장 작은 높이**를 보고. 32px가 통과하지 못하면 패널 확대가 필요하다는 근거로 쓰고, 화면 변경은 따로 결정 | 240px에서도 적중률 < 60%: 질문 영역 판정만 빼고 `ui`/`offscreen`은 유지(시선 기능 전체는 포기하지 않음) |
| 거리 변화 | ±10cm에서 `e50` ≤ 기준의 1.5배이거나, 표본의 80% 이상이 `position_changed`로 막힘(틀린 값을 조용히 내지 않음) | `e50` > 2배인데 막힌 표본 < 50% |
| H3 주기(주기별) | 실제 주기 ≥ 목표의 90%, 추론 p95 ≤ 주기의 1/3, 지연 오차 p95 ≤ 50ms, 긴 작업 ≤ 2개/10초 → 통과한 가장 높은 주기를 기본 후보로 | 초당 10회도 통과하지 못하면 시선 분석은 초당 4회(또는 적응형, 상한 낮춤) |
| H3 D 호환 | 자동 테스트에서 D 요약 동일(격자 한 칸 안). 실제 웹캠에서 D 검출 비율 차이 ≤ 3%p(참고) | 자동 테스트 불일치 → 격자 선택 수정 전까지 진행하지 않음 |

- 판정 사이(통과도 실패도 아님)는 "결론 없음"으로 보고하고, 조건 추가(다른 사람·조명) 여부를 사용자가 정한다.
- 결과는 `docs/progress.md`에 적는다.
- 그 뒤 G1 포함 여부, 질문 패널 크기, 기본 주기를 정하고 1단계(본 구현) 계획을 고친다.

## 14. 테스트와 검증

결과를 보고할 때 **가짜 검출기 자동 테스트**(배선·계산·흐름)와 **실제 MediaPipe·실제 웹캠 측정**(정확도)을 구분한다. 실측하지 않은 정확도를 보장 수치로 쓰지 않는다.

**계산 테스트** (`web/e2e/gaze-math.spec.ts`)
- 특징: 픽셀 보정(4:3·16:9), 눈 좌표계 회전, 반전 규약.
- 릿지: 계수 복원, λ, 특이 행렬.
- 묶음 교차 검증: 같은 묶음의 프레임이 학습·검증에 동시에 들어가지 않음. 들어가면 실패하는 테스트로 확인.
- 모델 선택: 곡선 데이터면 M2, 아니면 M1.
- 로지스틱: 분리 가능·불가능 데이터, 클래스 가중치, 임계값 규칙, AUC, 분포 밖.
- 영역 판정: 여유·우선순위·판정 불가 영역. 사유별 `unknown`, 평활·히스테리시스.
- 요약: 답변 시간과 분석 시간, `unknown` 제외, 기준점.
- D 격자: 4·10·15회 입력에서 D 요약 동일. 적응 정책. 뷰포트·배율 변경 무효화.

**브라우저 e2e** (가짜 검출기 `gaze` 모드: 숨긴 정답 사상 + 잡음으로 홍채·눈꺼풀·고개 특징점을 만들고, 화면의 점·렌즈 위치를 "본다")
- 렌즈 대 화면 위쪽: 가짜 렌즈 응시와 위쪽 띠 응시가 구별되는 설정, 구별되지 않는 설정 → 두 번째에서 G1이 "구별할 수 없음".
- 처음 보는 점 오차.
- 고개 자세별, 카메라 거리 변화(가짜 얼굴 크기 변경 → `position_changed`).
- 창 크기 변경(`page.setViewportSize`)과 배율 변경(무효화 함수에 배율 값을 바꿔 넣음. 실제 확대/축소는 수동 시험).
- 품질 낮은 보정 → 사용 안 함, 보정 건너뜀 → 결과 없음.
- 다시 보정·보정 지우기·카메라 끔 → 정리.
- 시선 동의 없이 시작 불가. 서버 요청 본문에 시선 값 없음.
- 기존 카메라·D·코칭·STT e2e 회귀, `npm run build`(진단·실험실·가짜 검출기 번들 제외), 백엔드 `pytest`.

**실제 웹캠 수동 시험**
- 0단계 절차(13절) + 1단계 뒤 보정 반복 일관성, 고개·눈 분리, 안경·조명, 창 크기·확대/축소, 카메라 끔.
- 결과는 사용자가 `docs/progress.md` 표에 적는다.

## 15. 위험과 한계

- 웹캠 시선 추정은 전용 장비보다 훨씬 부정확하다. 이 앱의 수치는 측정 전에는 모른다.
- 한 줄 질문은 판정하지 못할 가능성이 크다.
- 노트북 렌즈와 화면 위쪽은 구별되지 않을 수 있다(H1로 시험).
- 안경 반사·어두운 조명·홍채를 가리는 눈꺼풀에서 세로 방향이 불안정할 수 있다.
- 자세가 바뀌면 다시 보정해야 한다.
- 저사양에서는 주기가 낮아진다. 실시간 표시가 방해될 수 있다(숨기기).
- 0단계는 한 사람·한 기계 결과라 일반화할 수 없다.
